# C1 — канонический идентификатор заметки (P0)

## Что сломано

У одной заметки сейчас **две личности**. Локально это `id` вида `local_<uuid>`
(`LocalStorageService.saveNew`), в облаке — отдельный идентификатор документа Firestore,
который хранится рядом как `linkedCloudId`. Ни один из них не является общим ключом:
локальный не существует для облака, облачный не существует, пока заметку не выгрузили,
и меняется, если облачную копию удалить и создать заново.

Производные ИИ (сводки, эмбеддинги, лента) ключуются по локальному `documentId`. Когда
они приезжают из облака, они приезжают с облачным. Поэтому в
`src/features/ai/services/AIRestoreService.ts` живёт **сшивка по содержимому**:

```ts
  const orphanSummaries = new Map<string, AIDocumentSummary>();
  for (const s of summaries) {
    if (!docIds.has(s.documentId) && s.contentHash) orphanSummaries.set(s.contentHash, s);
  }
  ...
      const orphan = orphanSummaries.get(hash);
      if (orphan) {
        const adopted: AIDocumentSummary = { ...orphan, documentId: doc.id };
        ...
        // Claimed — two notes with identical text must not both take it.
        orphanSummaries.delete(hash);
```

Комментарий сам называет провал: если у двух заметок одинаковый текст, сводку заберёт
та, что попалась первой. Одинаковый текст — не экзотика: шаблон, копия, две пустые
заметки. И это единственный способ, которым производные находят свою заметку после
восстановления.

Переезд на Supabase упирается в то же самое. Манифест переноса должен назвать каждую
заметку так, чтобы обе стороны согласились, что это она. Ни `local_…`, ни идентификатор
Firestore для этого не годятся.

## Что делать — и чего НЕ делать

**Не переименовывать существующие ключи.** Соблазн сделать `id` документа равным
облачному идентификатору (или наоборот) выглядит чище, но это перекладывание ключей сразу
в двух базах, у живого пользователя, без возможности откатиться. Мы этого не делаем.

Вместо этого: **добавить каждой заметке поле `uuid` — стабильное, генерируемое клиентом
один раз и никогда не меняющееся.** Локальный `id` и `linkedCloudId` остаются как есть и
продолжают работать. `uuid` — это то имя, о котором договариваются обе стороны: он
попадает в облачный документ, в манифест переноса и в производные ИИ. Поле
необязательное, поэтому **подъём версии IndexedDB не нужен**.

Три отдельных коммита, в этом порядке. После каждого приложение должно работать.

### C1.1 — новые заметки получают `uuid`

`src/core/storage/localDb.ts`, интерфейс `LocalDocument`, сразу после `id`:

```ts
export interface LocalDocument {
  id: string;
  /** Канонический идентификатор заметки: генерируется клиентом один раз и не
   *  меняется никогда. Локальный id и linkedCloudId — адреса в двух разных
   *  хранилищах; uuid — само имя заметки, о котором договариваются обе стороны.
   *  По нему ключуются производные ИИ и манифест переноса. Необязателен, пока
   *  не заполнен у всех заметок (см. C1.2). */
  uuid?: string | undefined;
```

`src/core/services/LocalStorageService.ts`, `saveNew` — в объект `docObj`, рядом с `id`:

```ts
    const docObj = {
      id: localId,
      uuid: randomUUID(),
      guestId: userId,
```

`randomUUID` в этом файле уже импортирован.

**Проверка.** Новый файл `src/core/services/__tests__/documentUuid.test.ts`:

### C1.2 — существующие заметки получают `uuid` один раз

Разовый проход при старте, идемпотентный, без обращений к облаку.

Новый метод в `src/core/services/LocalDocumentService.ts`, рядом с `_updateProfile`:

```ts
  /** Проставляет uuid заметкам, созданным до C1.1. Идемпотентно: заметку с уже
   *  заполненным uuid не трогает. Локальная операция — облако не читается, чтобы
   *  проход не стоил квоты чтений. */
  async backfillDocumentUuids(guestId: string): Promise<number> {
    const db = await getLocalDb();
    const docs = await db.getAllFromIndex('documents', 'by-guest', guestId);
    const missing = docs.filter(d => !d.uuid);
    if (missing.length === 0) return 0;

    const tx = db.transaction('documents', 'readwrite');
    await Promise.all(missing.map(d => tx.store.put({ ...d, uuid: randomUUID() })));
    await tx.done;
    return missing.length;
  },
```

`randomUUID` в этом файле уже импортирован (первая строка), добавлять ничего не нужно.

Вызов — там же, где приложение уже делает разовые локальные проходы при входе
пользователя. **Найди это место сам** (посмотри, откуда вызывается
`LocalDocumentService._updateProfile` или похожие восстановительные проходы) и вызови
оттуда, обернув в `try/catch` с `reportError`. Новых точек входа не создавай, при старте
ничего не блокируй: проход локальный и быстрый, но падать из-за него приложение не должно.

**Проверка.** Дополни `documentUuid.test.ts`:

```ts
  it('backfills notes created before the field existed, and only those', async () => {
    const db = await getLocalDb();
    await db.put('documents', {
      id: 'local_old', guestId: 'u1', title: 'n', currentVersion: 1, totalWords: 1,
      totalDuration: 0, sessionsCount: 1, firstSessionAt: 1, lastSessionAt: 1, tags: [],
    } as never);
    await db.put('documents', {
      id: 'local_has', guestId: 'u1', uuid: 'keep-me', title: 'n', currentVersion: 1,
      totalWords: 1, totalDuration: 0, sessionsCount: 1, firstSessionAt: 1,
      lastSessionAt: 1, tags: [],
    } as never);

    const filled = await LocalDocumentService.backfillDocumentUuids('u1');

    expect(filled).toBe(1);
    expect((await db.get('documents', 'local_old'))!.uuid).toBeTruthy();
    // Уже назначенный uuid не переписывается никогда: он и есть имя заметки.
    expect((await db.get('documents', 'local_has'))!.uuid).toBe('keep-me');
  });

  it('is idempotent', async () => {
    await LocalDocumentService.backfillDocumentUuids('u1');
    expect(await LocalDocumentService.backfillDocumentUuids('u1')).toBe(0);
  });
```

### C1.3 — `uuid` доезжает до облака

Найди, где локальный документ превращается в облачный (`StorageService.addCloudCopy` и
то, что пишет метаданные документа в `CloudSyncService`), и добавь `uuid` в записываемые
поля. **Осторожно с двумя вещами:**

1. `firestore.rules` ограничивает набор полей документа. Если правила перечисляют
   допустимые ключи — добавь `uuid` туда же, иначе запись начнёт отбиваться с
   `permission-denied`, и это будет выглядеть как проблема авторизации, а не схемы.
   Проверь `firestore.rules` (332 строки) прежде чем писать код.
2. Обратное направление (`addLocalCopy`, восстановление из облака) должно **принимать**
   `uuid`, если он там есть, и не затирать локальный, если в облаке пусто.

Сшивку по содержимому в `AIRestoreService` **в этом коммите не удалять**: пока `uuid`
проставлен не у всех и не везде доехал, она остаётся единственным способом подобрать
осиротевшие производные. Её снятие — отдельная задача после переезда.

**Проверка.** Тест на то, что выгрузка кладёт `uuid`, а загрузка его не затирает.
Опирайся на существующие тесты `addCloudCopy` в
`src/features/writing/__tests__/storageService.test.ts` — там уже настроены моки
Firestore, повтори их способ.

# C2 — схема SQL и RLS в репозитории

## Что нужно

Целевая база — Supabase (Postgres). Сейчас в репозитории нет ни схемы, ни политик
доступа. Правила Firestore (`firestore.rules`, 332 строки) — **это спецификация**, а не
черновик: они описывают, кто и что может читать и писать, и переписывать их «по памяти»
на новом языке нельзя. Переноси построчно.

## Что делать

Создать каталог `supabase/migrations/` и в нём **версионированные** файлы миграций —
нумерованные, применяемые по порядку, никогда не редактируемые задним числом:

- `0001_schema.sql` — таблицы: `documents`, `versions`, `drafts`, `ai_summaries`,
  `ai_embeddings`, плюс то, что реально есть в `firestore.rules` и в `localDb.ts`.
  Ключ документа — `uuid` из C1 (`uuid primary key`, не `serial`). Поля с шифротекстом
  хранить как `text`, ничего не разбирая: клиент шлёт то, что зашифровал.
- `0002_rls.sql` — включить RLS на каждой таблице (`alter table … enable row level
  security`) и завести политики по образцу правил Firestore.

**Свериться с `firestore.rules` явно.** В комментарии над каждой политикой — ссылка на
строку правил, из которой она взята. Где правило Firestore не выражается политикой
один-в-один — не выдумывай, выпиши в отчёт.

Отдельно проверь по правилам: чтение черновиков только владельцем (это чинили как
находку аудита), и запрет админского чтения чужих данных там, где он запрещён.

## Проверка

Негативные тесты обязательны — политика, которую не пробовали обойти, не проверена.
Файл `supabase/tests/rls.test.sql` (или тесты через клиент, если так удобнее): для каждой
таблицы — попытка прочитать и изменить строку **чужого** пользователя, ожидание нуля
строк и отказа.

**Если у тебя нет возможности поднять локальный Postgres/Supabase и прогнать эти
тесты — так и напиши в отчёте и остановись на схеме.** Не пиши «тесты написаны» про
тесты, которые ни разу не запускались; на этом уже дважды попадались. Ненадёжная схема
хуже отсутствующей: на неё будут опираться при переезде.

# C3 + C4 — манифест переноса

## Что нужно

Экспорт, который забирает **всё**, и его опись. Пункты C3 и C4 бэклога — это одна
задача, потому что ответ на C4 объясняет форму C3: серверный экспорт Firestore не видит
данных, живущих только в браузере (незалогиненные заметки, невыгруженные версии,
черновики, производные ИИ). Значит экспорт **обязан выполняться в клиенте**, а не на
сервере.

## Что делать

Новый модуль `src/features/settings/services/migrationExport.ts`. Требования, каждое
из которых — следствие уже пережитой ошибки:

1. **Все версии, а не только последняя.** История версий — это и есть заметка.
2. **Шифротекст переносится как есть.** Не расшифровывать. Если хранилище заперто —
   экспорт всё равно должен пройти: шифротекст переносим не читая. Заодно это значит,
   что экспорт не требует пароля.
3. **Счётчики и контрольные суммы до и после.** Сколько документов, версий, черновиков,
   производных; sha-256 содержимого каждой версии. Без них «перенеслось» — это мнение.
4. **Список пропущенного, явный.** Всё, что не удалось прочитать, попадает в
   `skipped: [{ store, id, reason }]`. **Пустой результат чтения — это не «данных нет».**
   Ошибку чтения нельзя записывать как отсутствие записи: именно этот класс ошибок был
   худшим в проекте.
5. **Возобновляемость.** Курсор в `localStorage`, чтобы прерванный экспорт продолжался,
   а не начинался заново.
6. Формат — JSON, одна запись верхнего уровня с `version` схемы манифеста внутри.

Ключ каждой заметки в манифесте — **`uuid` из C1**. Ни `local_…`, ни идентификатор
Firestore.

## Проверка

Тесты на: наличие всех версий (не только последней), сохранение шифротекста байт в байт,
попадание нечитаемой записи в `skipped` (а не молча в «ничего не было»), совпадение
счётчиков, продолжение с курсора.

**Ключевой тест на невакуумность:** сделай так, чтобы чтение одного хранилища бросало
исключение, и убедись, что запись появилась в `skipped`, а общий счётчик её не потерял.

# C5 — рантайм на VPS: файлы, не развёртывание

## Что нужно

Сейчас `api/chat.ts` и `api/csp-report.ts` живут как функции Vercel. На VPS им нужен
процесс, надзор за ним и обратный прокси. В этой задаче — **только файлы в репозитории.
Ничего не разворачивать.**

## Что делать

Каталог `deploy/` со следующим:

- **`deploy/nginx.conf`** — TLS, заголовки безопасности (свериться с тем, что уже
  отдаётся сейчас — это блок `headers` в `vercel.json`, три группы правил; переноси
  их, а не выдумывай новые), SPA-fallback на `index.html`, отдельная политика кэша для `/sw.js`
  (**никогда не кэшировать** — иначе застрявший service worker держит старый бандл; на
  этом уже был инцидент «заметки пропали»), запрет отдачи `*.map`.
- **`deploy/justwriting.service`** — unit systemd для процесса API: рестарт при падении,
  переменные окружения из файла, не от root.
- **`/health` и `/ready`** — два разных эндпойнта, и разница между ними существенна:
  `/health` отвечает «процесс жив», `/ready` — «зависимости доступны, можно слать
  трафик». Добавь их в API-процесс.
- **`deploy/README.md`** — что и куда ставится, какие переменные окружения нужны, как
  проверить, что поднялось.

Секретов в репозитории быть не должно: только имена переменных и пример файла
`.env.example` без значений.

## Проверка

Развернуть нельзя — значит проверяем то, что можно:

- `nginx -t -c deploy/nginx.conf` (если nginx доступен локально) либо явно напиши в
  отчёте, что синтаксис не проверялся;
- эндпойнты `/health` и `/ready` покрыть тестом;
- сверить список заголовков безопасности с текущим прод-конфигом и **выписать в отчёт
  различия** — если что-то отдаётся сейчас и не отдаётся в новом конфиге, это регресс
  безопасности при переезде.
