# G1 — экспорт забирает 5 хранилищ из 25 (P0)

## Что сломано

`src/features/settings/services/migrationExport.ts`, строка 102:

```ts
    const order = ['documents', 'drafts', 'aiSummaries', 'aiEmbeddings'] as const;
```

Плюс `versions` через индекс. Итого пять. В IndexedDB их двадцать пять.

Не попадает в экспорт ничего из этого:

```
aiDialogues  aiDialogueEvents  aiChatMemory  aiCommitments  aiThreads
aiTimeline   aiBeliefs         aiBeliefRejections  aiPeopleIndex  aiPortrait
aiProfileFacets  aiThemeLedger  aiMonthlyDigest  aiDomainVectors  aiPersonas
aiInjectionJournal  lifeStory  profile  pending_sessions  syncQueue
```

Это ровно та категория, ради которой пункт C4 и существовал: **данные, живущие только в
браузере**. Серверный экспорт Firestore их не видит — но и наш клиентский экспорт тоже,
потому что он забрал именно те хранилища, у которых и так есть облачная копия. Форма
верная, содержание — нет.

Симметрично на стороне базы: `supabase/migrations/0001_schema.sql` описывает 12 таблиц,
портированных из `firestore.rules`. Тем пятнадцати хранилищам, что живут только в
браузере, в целевой схеме просто некуда приехать.

## Что делать

### G1.1 — общий дамп вместо пятнадцати типизированных блоков

Сейчас каждое хранилище в манифесте — своя `interface` и свой блок кода. Повторять это
двадцать раз не нужно и не надо: для данных, которые никто не разбирает по полям,
**нужен дословный перенос, а не типизированная схема**. Их задача — пережить круг
«выгрузили → залили» без потерь.

Добавь в `migrationExport.ts` рядом с существующими типами:

```ts
/** Хранилища, которые переносятся дословно. Их содержимое нигде на сервере не
 *  разбирается по полям — от них требуется пережить круг «выгрузили → залили»
 *  без потерь, а не лечь в типизированную схему. Заводить под каждое свой
 *  интерфейс значит писать двадцать блоков ради данных, которые никто не
 *  читает по частям. */
const VERBATIM_STORES: { store: string; keyPath: string }[] = [
  { store: 'aiDialogues', keyPath: 'id' },
  { store: 'aiDialogueEvents', keyPath: 'dialogueId' },
  { store: 'aiChatMemory', keyPath: 'id' },
  { store: 'aiCommitments', keyPath: 'id' },
  { store: 'aiThreads', keyPath: 'id' },
  { store: 'aiTimeline', keyPath: 'documentId' },
  { store: 'aiBeliefs', keyPath: 'id' },
  { store: 'aiBeliefRejections', keyPath: 'id' },
  { store: 'aiPeopleIndex', keyPath: 'key' },
  { store: 'aiPortrait', keyPath: 'id' },
  { store: 'aiProfileFacets', keyPath: 'id' },
  { store: 'aiThemeLedger', keyPath: 'id' },
  { store: 'aiMonthlyDigest', keyPath: 'month' },
  { store: 'aiDomainVectors', keyPath: 'cacheKey' },
  { store: 'aiPersonas', keyPath: 'id' },
  { store: 'aiInjectionJournal', keyPath: 'id' },
  { store: 'lifeStory', keyPath: 'eventDate' },
  { store: 'profile', keyPath: 'guestId' },
];

export interface VerbatimRecord {
  store: string;
  key: string;
  /** Запись как есть. Шифротекст не расшифровывается, поля не переименовываются. */
  payload: unknown;
}
```

`syncQueue` и `pending_sessions` в список **намеренно не входят**: это очередь
незавершённой работы этого устройства, а не данные пользователя. Переносить её на новый
бэкенд нельзя — задачи ссылаются на идентификаторы Firestore, которых там не будет.
Напиши это комментарием рядом со списком, чтобы никто не «дополнил» его позже.

Дальше — один блок вместо двадцати, после существующих блоков и до сборки манифеста:

```ts
  // ── хранилища, переносимые дословно ───────────────────────────────────
  const verbatim: VerbatimRecord[] = [];
  for (const { store, keyPath } of VERBATIM_STORES) {
    if (doneStores.has(store)) continue;
    if (!db.objectStoreNames.contains(store)) continue;   // схема младше этого клиента
    try {
      const all = await db.getAll(store as never);
      for (const raw of all) {
        try {
          const key = String((raw as Record<string, unknown>)[keyPath] ?? '');
          verbatim.push({ store, key, payload: raw });
          checksums[`${store}:${key}`] = await sha256Hex(JSON.stringify(raw));
        } catch (e) {
          // Не смогли прочитать запись — это НЕ «записи нет». Молчаливое
          // превращение сбоя чтения в отсутствие данных — худший класс ошибок
          // в этом проекте, и здесь он стоил бы всей памяти ИИ.
          skipped.push({ store, id: '?', reason: String(e) });
        }
      }
      setCursor(store, String((all.at(-1) as Record<string, unknown>)?.[keyPath] ?? ''));
    } catch (e) {
      skipped.push({ store, id: '*', reason: String(e) });
    }
  }
```

И в `order` (строка 102) добавь все эти хранилища **после** существующих четырёх — иначе
возобновление с курсора будет считать их уже сделанными.

В `MigrationManifest` добавь поле `verbatim: VerbatimRecord[]` и счётчик на каждое
хранилище: `counters.verbatim: Record<string, number>`. Без счётчиков «перенеслось» —
это мнение, а не факт.

### G1.2 — куда это приедет

`supabase/migrations/0003_local_store_records.sql`, новый файл (существующие миграции
**не редактировать**, они версионированные):

```sql
-- Данные, живущие только в браузере: диалоги с ИИ, память чата, портрет,
-- грани профиля, история жизни и прочее. На сервере их никто не разбирает по
-- полям, поэтому пятнадцать типизированных таблиц были бы схемой ради схемы.
-- Одна таблица с payload jsonb принимает их дословно; если что-то из этого
-- когда-нибудь понадобится серверу, оно выделится в свою таблицу отдельной
-- миграцией.
create table if not exists public.local_store_records (
  user_id  uuid not null references auth.users(id) on delete cascade,
  store    text not null,
  key      text not null,
  payload  jsonb not null,
  checksum text,
  primary key (user_id, store, key)
);

alter table public.local_store_records enable row level security;
```

Политики RLS — в том же файле, по образцу `0002_rls.sql`: читать, вставлять, изменять и
удалять может только владелец (`auth.uid() = user_id`), больше никто. Никаких исключений
для администратора: в `firestore.rules` такое исключение для черновиков уже оказалось
дырой, и повторять его не надо.

## Тесты

Дополни `src/features/settings/services/__tests__/migrationExport.test.ts`:

- в манифест попадает запись из хранилища, которого раньше в экспорте не было

- счётчик по этому хранилищу совпадает с числом записей;
- **сбой чтения хранилища даёт запись в `skipped`, а не тишину** — сделай так, чтобы
  `getAll` для одного хранилища бросал, и проверь, что оно названо в `skipped`;
- `syncQueue` в манифест **не** попадает, даже если в нём есть записи.

**Проверка на невакуумность:** убери блок `verbatim` — первый тест обязан упасть.

намеренно сломанная политика. Для этого: временно убери одну политику `select` из

# G4 — производные ИИ до сих пор ищут свою заметку по хешу содержимого (P2)

## Что сломано

C1 завела заметке канонический `uuid`, но в `src/features/ai/` он не используется нигде.
Сводки и эмбеддинги по-прежнему ключуются локальным `documentId`, а после восстановления
из облака привязываются сшивкой по хешу текста —
`src/features/ai/services/AIRestoreService.ts`, около строки 215:

```ts
    if (!docIds.has(s.documentId) && s.contentHash) orphanSummaries.set(s.contentHash, s);
    ...
        // Claimed — two notes with identical text must not both take it.
        orphanSummaries.delete(hash);
```

Комментарий сам называет провал: у двух заметок с одинаковым текстом сводку заберёт та,
что попалась первой. Одинаковый текст — это шаблон, копия, две пустые заметки.

Я отложил это сам в тикете C1 и был прав: пока `uuid` не проставлен у всех, сшивка —
единственный способ подобрать осиротевшие производные. Сейчас `uuid` проставляется новым
заметкам и добивается старым, так что можно переходить.

## Что делать

**Не удалять сшивку.** Понизить её до запасного пути.

1. При создании и при сохранении сводки и эмбеддинга класть рядом `documentUuid` — брать
   его из документа. Поле необязательное, версию IndexedDB поднимать не нужно.
2. В `reattachOrphanedAnalysis` сначала искать по `documentUuid`, точным совпадением.
   Только для записей, у которых `documentUuid` пуст, оставлять сшивку по `contentHash`.
3. Комментарий над запасным путём переписать: сказать, что он для записей, созданных до
   появления `uuid`, и что для них риск «две заметки с одинаковым текстом» сохраняется.

Сравнение по `uuid` должно быть **строгим**: совпадает — берём, не совпадает — не берём.
Никаких «если uuid не нашёлся, попробуем по хешу» для записи, у которой uuid есть: это
вернуло бы ту же ошибку через заднюю дверь.

## Тест

В `src/features/ai/services/__tests__/AIRestoreService.test.ts` (он уже есть):

- две заметки с **одинаковым текстом** и разными `uuid`, две осиротевшие сводки с
  соответствующими `documentUuid` → каждая уезжает к своей заметке. Это тот самый
  случай, на котором ломается сшивка по хешу;
- запись без `documentUuid` по-прежнему подбирается по `contentHash` — запасной путь жив;
- запись с `documentUuid`, которому нет соответствия, **не** подбирается по хешу.

**Проверка на невакуумность:** убери ветку с `documentUuid` — первый тест обязан упасть.

Поднять покрытие `src/features/auth/services/**` до уровня, на котором имеет смысл
поставить порог. **Не гнаться за процентом**: писать тесты на поведение, которое

Приоритет — случаи с уже известной ценой:
- выход из аккаунта при наличии несинхронизированных данных (A1) — путь `force`;
- перенос гостевых заметок и черновика (A8) — случай, когда черновик уже есть у

`src/core/storage`, `src/core/crypto` и `src/core/services`. Цифры возьми из своего
прогона и приведи в отчёте.

## Что считается выполнением

Не «покрытие выросло на N», а перечень: какие сценарии теперь проверяются и какой из них
падал бы на соответствующей ошибке. Тест, который не падает ни на одной правдоподобной
поломке, покрытие поднимает, а защиты не даёт.

# Чего в этом тикете намеренно нет

**Пункт C6 бэклога** — проверенные бэкап и восстановление, отработанный откат, критерии
go/no-go. Это не код: решение о том, при каких условиях переезжать и когда откатываться,
принимает владелец. Как только оно принято, из него получится обычный тикет.

**Снятие сшивки по хешу полностью.** G4 её понижает, но не убирает: записи, созданные до
`uuid`, останутся. Убрать её можно будет после переезда, когда станет видно, что таких
записей не осталось.
