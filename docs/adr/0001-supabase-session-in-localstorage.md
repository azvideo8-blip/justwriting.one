# ADR-0001: Сессия Supabase в localStorage

**Статус:** Принято, 2026-09-27
**Билет:** SA-5 (`docs/ag-tickets-2026-09-27-scratch-audit.md:58-61`)

## Контекст

justwriting — офлайн-PWA дневник (свой self-hosted Supabase, свой Node API в `api/`).
Внешний аудитор отметил, что auth-сессия (access + refresh токен) переживает перезапуск
браузера в `localStorage`, и попросил записать, почему это приемлемо в нашей модели угроз.

## Решение

Оставляем `persistSession: true` (`src/core/supabase/client.ts:27`): сессия хранится в
`localStorage` стандартным адаптером `@supabase/supabase-js` v2 — в `client.ts` не задан
ни кастомный `storage`, ни `storageKey`, ни `authStore`, значит библиотека пишет сессию
в `window.localStorage` под ключом `sb-<url-prefix>-auth-token`. Токен обновляется молча:
`autoRefreshToken: true` (`client.ts:28`), плюс явный `refreshSession()` в
`getIdToken` (`src/core/auth/supabaseAuthProvider.ts:106-116`).

## Почему так

- **Офлайн без обращения к серверу.** Приложение — PWA: сервис-воркер
  (`public/inline-init.js:2`, `public/sw.js:37-51`) отдаёт оболочку без сети, данные живут
  в IndexedDB, синхронизация — отдельный явный тумблер (`src/core/sync/cloudSyncEnabled.ts:15`).
  Стартовать и писать в локальный архив человек должен при доступности сервера авторизации
  равной нулю. Сессия в `localStorage` — единственный вариант, при котором перезапуск
  без сети не выбрасывает на экран входа и не блокирует локальные данные.
- **Свой Supabase, не сторонний бэкенд.** Токен уходит только туда, что на нашем же
  origin: Supabase проксируется нашим nginx (`/auth/`, `/rest/`, `/realtime/`),
  `/api/*` — наш же Node API; в `callAi` токен едет заголовком
  `Authorization: Bearer` на `/api/<имя>` (`src/core/ai/callAi.ts:57`). Сторонних получателей
  токена в репо нет.
- **PKCE вместо implicit.** `flowType: 'pkce'` (`client.ts:25-34`): токены обмена не попадают
  во фрагмент URL, в Referer и в историю браузера. `detectSessionInUrl: true` нужен ссылкам
  восстановления и приглашений (`supabaseAuthProvider.ts:202-214, 216-224`).
- **Альтернатива (httpOnly-cookie) — не рассмотрена до конца и честно помечена так.**
  supabase-js v2 сам управляет сессией на клиенте; перевод на httpOnly-cookie означал бы
  перестройку всего auth-слоя и своего проксирования токенов через nginx + Node API.
  Известные обходы вокруг Kong/CORS для cookie-сессий self-hosted Supabase в этом репо
  мы не проверяли — утверждать про них ничего не будем. Для гостевого и офлайн-режима
  cookie-сессия всё равно требовала бы живого сервера на каждом старте.

## Модель угрозы

**Атакующий:** XSS в браузере владельца (тот же origin). Он читает `localStorage` —
то есть получает access+refresh токен.

**Что даёт украденный токен:** чтение/запись строк **одного** аккаунта в рамках RLS
(`supabase/migrations/0002_rls.sql`) и вызовы нашего `/api/*` с его квотами. Целостность
данных под угрозой — это главный реальный риск решения.

**Чего токен НЕ даёт — blast radius ограничен шифрованием (проверено по коду):**
всё облачное шифруется на клиенте AES-GCM-256 (`src/core/crypto/encrypt.ts:137-156`),
сейф создаётся автоматически при первом входе из пароля человека
(`src/features/auth/services/AuthService.ts:51-66`), а разгон без сейфа запрещён
(EA-16, `src/core/crypto/cryptoHelpers.ts:37-42`). В `users.encryption_meta` лежит
**обёрнутый** ключ: salt + wrappedDataKey, AES-KW, PBKDF2 600k (`encrypt.ts:1, 40-78`;
распаковка — `AuthService.ts:222-245`). Ключ разворачивается только паролем сейфа,
который нигде не хранится; на сервер авторизации уходит вообще производное от него
значение (EA-15), из которого ключ сейфа не получить (`src/core/auth/authSecret.ts:3-11`).
Итог: токен без пароля человека = шифртекст + метаданные, не читаемый дневник.
Админ-выборка колонок ключевой материал не отдаёт
(`src/core/data/providers/fields.ts:161-167`).

**Чем закрыт сам XSS (на что опирается решение):**
- вывод ИИ — только через `rehype-sanitize` со строгим списком тегов, без `img`;
  `rehype-raw` запрещён комментарием в том же файле и по репо не встречается
  (`src/features/ai/components/MarkdownRenderer.tsx:3, 6-8, 10-20, 33`);
- ответ модели зачищается от любого HTML на сервере (`api/ai/pure.ts:8, 31, 71`, DOMPurify);
- CSP `script-src 'self'` без unsafe-inline/unsafe-eval, плюс `frame-ancestors 'none'`,
  `base-uri 'self'`, `report-uri` (`deploy/nginx.conf:257`; отдельно для sw.js —
  `deploy/nginx.conf:237`);
- заголовки: HSTS, nosniff, X-Frame-Options DENY, COOP/CORP same-origin
  (`deploy/snippets/security-headers.conf`);
- сырой HTML в DOM рендерит только `GuidePage.tsx:138` (`dangerouslySetInnerHTML`) —
  источник: наши же статические `/docs/*.html` с того же origin, причём перед вставкой
  вырезаются `<script>` и все `on*`-атрибуты (`GuidePage.tsx:35-38`). Чужих данных
  этот путь не касается.

**Остаточный риск, называем прямо:** если в момент XSS сейф открыт в этой вкладке,
шифрование атакующему не помеха — тот же origin читает уже расшифрованное из памяти.
Осложняет жизнь но не отменяет это: автоблокировка простоя 15 мин / 1 ч для «запомнить
устройство» (`src/core/crypto/useEncryptionStore.ts:17-21`), блокировка при `pagehide`
(`useEncryptionStore.ts:111-117`), «запомненный» ключ — неэкстрагируемый CryptoKey в
отдельном IndexedDB, вывести его нельзя, использовать — да
(`src/core/crypto/keyVaultCache.ts:1-7`). Выход из сессии отзывает токены
(`supabaseAuthProvider.ts:170-185`). Расположение сессии (localStorage vs cookie) на эту
ветку риска не влияет вообще.

## Когда пересматривать

1. Любой путь рендера чужого/пользовательского HTML: появление `rehype-raw` или
   `dangerouslySetInnerHTML` на данных, пришедших не из репо (сейчас единственный —
   статические страницы руководства, см. выше).
2. Мультипользовательский доступ: шаринг заметок, совместные ссылки — blast radius
   перестанет быть «только мой дневник».
3. Любой путь, где токен уходит заголовком стороннему сервису (сейчас — только наш
   `/api/*` и свой Supabase через наш же nginx).
4. Переезд с self-hosted Supabase на managed/Cloud с другой моделью токенов или политикой
   хранения сессии.
5. Смена storage-адаптера сессии (`storage`/`storageKey`/`authStore` в `client.ts`) —
   тогда этот ADR переписывается под новое фактическое хранилище.

## Примечание о площади

Одностраничное требование билета. Каждая ссылка выше — файл:строки проверенного факта;
отдельного списка литературы нет намеренно, чтобы расхождение строк не плодить.
